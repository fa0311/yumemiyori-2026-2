# 執筆に専念するための技術同人誌テンプレートの設計

技術同人誌を製作するとき、「本文を書く」以外の作業負担が大きいです。本の製作は執筆だけでなく、組版の調整、目次や奥付の生成など、いくつもの工程があります。本誌のように複数の執筆者がいる場合は、それぞれの記事の調整もあります。これらは本編の執筆と同じくらい大事ですが、どうしても「本文を書く」ことから意識が離れてしまいます。

本誌の製作では、そうした作業をできるだけ自動化しています。執筆者は自身の記事を書くだけです。技術同人誌を作る現場で起きる「非執筆コスト」を削減するように、製作プロジェクトを設計しています。

本誌の製作プロジェクトは執筆テンプレートとして、公開しています。本記事では、そのテンプレートの目的、どのような仕組みで自動化しているのかを、実際のファイル構成と処理の流れにそって説明します。手作業の編集作業が必要になる部分も含めて、どこまで自動化できて、どこからが人手が必要なのかを整理していきます。

## 執筆テンプレートの製作

技術同人誌は、ブログ記事や社内ドキュメントと違い、体裁を整えた書籍として完成させる必要があります。たとえば、次のような作業が発生します。

- 組版（レイアウト）をどうするか
- 記事をどう管理するか
- 奥付に書く項目をどう管理するか
- 表紙画像や PDF の出力設定をどうするか

これらは「本文を書く」とは別の作業ですが、最終的に雑誌自体の品質に直結します。目次や組版などの作業負荷が積み重なると、本来注力すべき執筆が疎かになりえます。そこで、執筆者が本文に集中できるようにと、執筆テンプレートを製作しました。

そのテンプレートは 2023 年ごろに、本の組版や製作を自動でおこなう仕組みとして公開しました。本誌の既刊もこのテンプレートを使って作成してきました。GitHub で管理し、記事の追加や構成の変更は PR ベースで行えるようにしています。

一方で、本誌のような複数人で製作する場合、１つの記事管理ファイルが同時に編集されるという問題ありました。特に締切間近で記事追加の PR が一斉に上がったときは、コンフリクトが毎回発生するため、またか...と頭を悩ませていました。

そこで、今年の夏に、記事管理を含めた自動化を大きく見直しました。執筆者が本文を書くことに集中しやすいように、記事の管理・目次・著者紹介・奥付の生成をより一貫した仕組みに整理し直しています。

## 執筆テンプレートの大まかな流れ

執筆テンプレートの目的は、技術同人誌の制作の「文章を書く」と「本全体の構成や体裁を整える」を分離することです。初回公開時には主に組版や体裁を自動でまかなうテンプレートとしてリリースしましたが、今年の夏に行った大規模な自動化改修では、より広い意味での製作工程の自動化を目指しています。

そのため、テンプレートの流れは次のように整理しています。

1. 執筆者が Markdown で記事を書く
2. Markdown のメタデータ Front Matter にタイトル・著者・プロフィールを記述する
3. 本の構成と目次の順番を YAML で定義する
4. 自動生成スクリプトが目次・著者紹介・奥付を作る
5. 必要に応じて手動で微調整して、PDF を出力する

この流れの重要なポイントは、執筆者が書くべき対象を「本文」だけに絞れることです。目次や著者紹介、奥付は基本的に自動化されるので、書籍の体裁に関する調整が執筆者の思考を妨げることが少なくなります。

最終的には「自動生成したものを人が微調整する」工程は残りますが、それは編集の最後の仕上げであり、執筆の本質ではありません。これはかなり前からやっていた雑務を削減し、執筆者の時間を本文へ向けさせるための設計です。

なお、表示作成はいまだに未対応です。今は生成 AI で自動生成させることもできますが、本誌は社内のデザイナーさんに依頼してます。毎回かっこいい表紙を仕上げてもらっています、改めてありがとうございます！

## テンプレートの全体像

このテンプレートの中心は、執筆者が Markdown で記事を書くと、それを本全体の構成に自動的に反映できるようにすることです。リポジトリの主要なファイル構成は次のとおりです。

```text
book/
└─ manuscripts/
   ├─ articles/
   ├─ config/
   │  ├─ articles.yml
   │  ├─ entry.yml
   │  └─ generate.yml
   ├─ generated/
   ├─ edited/
   └─ pages/
```

ここでは、役割が大きく分かれます。

| ディレクトリ | 役割 |
|:--|:--|
| `articles/` | 執筆者が本文を書き込む場所 |
| `config/` | 本の構成や見た目のルールを定義する場所 |
| `generated/` | 自動生成される目次・著者紹介・奥付の原本 |
| `edited/` | 手動で微調整するための編集用コピー |
| `pages/` | はじめにやあとがきなどの固定ページ |

執筆者が主に触れるのは `articles/` です。ここに Markdown ファイルを置くだけで、テンプレート側が自動で対象として認識し、必要な生成処理に取り込めます。

一方で、`config/` は編集者や製作担当が管理する領域です。ここで、本の構成順と生成時の見た目を定義します。

| 設定ファイル | 役割 |
|:--|:--|
| `articles.yml` | 記事の順番を制御する。ファイルが無い場合は、`articles/` 配下の Markdown ファイルをファイル名順で自動的に扱う。 |
| `entry.yml` | 本全体の構成順を定義する。目次や固定ページ、記事一覧の配置順などを決める。 |
| `generate.yml` | 著者紹介や奥付のテンプレートを定義する。本文の内容ではなく、書籍としての見せ方を決める。 |

さらに、本のタイトルや著者名などの書籍情報は `book/vivliostyle.config.js` で定義します。これは記事の中身ではなく、本全体のメタ情報を管理する場所です。

この設計では、執筆者は「どこに何を書けばいいか」を知っていれば十分です。執筆の本質は本文そのものに集中し、構成や体裁、目次や奥付の整合はテンプレート側が担います。編集者が YAML を調整するだけで、製作工程の多くを自動化できる、というのがこのテンプレートの大きな特徴です。

## 4. 文章から本の骨格を作る

このテンプレートの肝は、各記事の front matter を読むことです。たとえば各記事は次のような形式で書きます。

```yaml
---
class: content
title: 技術同人誌の執筆に集中するためのテンプレート設計
author: 江本光晴
profile: |
  日頃は iOS アプリの開発をやっています。
---
```

ここで `title` と `author` と `profile` が、後段の自動生成に利用されます。たとえば著者紹介ページでは、各記事の著者名とプロフィールが集約されます。目次ではタイトルが自動取得されます。奥付にも本名や版情報が入ります。

これは大きな利点があります。本文ファイルのメタ情報を一か所に書いておくことで、目次や著者紹介などが常に同期されるからです。

本当に大事なのは、これが「書いたあとに誰かが手作業でまとめ直す」ものではなく、構造的に自動生成されるという点です。執筆者がタイトルを変えるだけで、目次が変わる。著者名を変えるだけで、著者紹介が変わる。これにより、書籍全体の整合性が自然に保たれます。

## 5. 自動生成されるページには何があるのか

このテンプレートでは、執筆者が直接編集する必要があるのは本編の Markdown に限られ、目次・著者紹介・奥付は自動生成されます。

### 5.1 目次

`book/manuscripts/generated/index.md` は、掲載順とページタイトルから目次を生成します。

`entry.yml` の定義をもとに、固定ページと記事一覧が一本の目次に展開されます。`articles` エントリがある場合は、その配下の記事タイトルが自動で並びます。

これにより、記事ファイルを追加しただけで、目次が再生成されます。人手で `index.md` を毎回更新しなくてよくなります。

### 5.2 著者紹介

`generated/authors.md` は、各記事の著者名とプロフィールを集約して、著者ごとの紹介ページを作ります。

一人の著者が複数の記事を書いていた場合でも、自動的にタイトルを1つの箇条書きにまとめます。プロフィールも `profile_template` で自由に書式を変えられます。

`profile_template` は次のような形式です。

```yaml
profile_template: |
  ### {author}（{title}）

  {profile}
```

ここにある `{author}` や `{title}` は、書籍中の各著者プロフィールを整えるためのテンプレート変数です。テンプレートを変えるだけで、著者紹介の見た目を切り替えられます。

### 5.3 奥付

`generated/colophon.md` は、書籍のタイトル、発行者、版履歴、連絡先などをまとめて生成します。

`generate.yml` に次のように定義しておけば、

```yaml
edition_history: 初版

colophon_rows:
  - label: 発行
    value: ゆめみより製作委員会
  - label: 連絡先
    value: https://x.com/yumemiinc
```

奥付の雛形が自動生成されます。ここでの大きな価値は、「奥付の項目がデータ化されている」ことです。手動でメモ帳を開いて調整する必要がなくなり、同じ構成を何度も書き直す心理的な負担が減ります。

## 6. 生成と編集の境界を分離する

ここでの設計では、「自動生成したファイルをそのまま編集する」のではなく、`generated/` から `edited/` にコピーして微調整できるようにしています。

`yarn edit` を実行すると、生成済みの目次や著者紹介などを `edited/` に複製します。これにより、

- 生成されたファイルは基本的に原本
- 人が最終調整したい場合は `edited/` で修正
- PDF ビルド時は `edited/` を優先して使う

という二層構造ができます。

この仕組みの意義は大きく、タイトルの自動生成と手動の仕上げが相互に干渉しないことです。たとえば、目次に微調整が必要な場合でも、生成スクリプトを再実行しても `edited/` で保護されているファイルは壊れません。

これは「自動化の利点を守る」ための設計です。自動生成を前提にしつつ、最後の手直しだけを人手で行えるようにする。これは技術書のメンテナンスとしてかなり合理的です。

## 7. 本の順番とページ構成も設定ファイルで管理する

`entry.yml` は本全体の構成を表す設定ファイルです。たとえば次のように定義します。

```yaml
- type: generated
  id: index
  toc: false

- type: page
  title: はじめに
  file: pages/preface.md
  toc: true

- type: articles
  toc: true

- type: generated
  id: authors
  toc: false

- type: generated
  id: colophon
  toc: false
```

ここには本の流れがすべて書かれています。

- 目次を最初に置く
- はじめにページを入れる
- 本文を並べる
- 著者紹介を入れる
- 奥付を最後に置く

こうして本の構造を明示しておくことで、執筆者は「どのファイルをどこに置くか」を意識しなくてよくなります。構成の責務が自動化のレイヤーに移るからです。

## 8. ビルドを簡単にし、出力を再現可能にする

このテンプレートでは、Markdown から PDF を生成するフローを簡潔にしています。

```shell
yarn build
```

これを実行すると、まず自動生成の対象が更新され、その後 Vivliostyle が本を PDF として出力します。つまり、本文の修正や記事の追加をしたあとに、ビルドを実行すればその場で全体の書籍として確認できるのです。

ここで便利なのは、実際の PDF 生成が逐次的な手作業ではなく、一つのコマンドで再現できることです。これにより、同人誌の生成結果が「人に依存する暗黙知」ではなく、コードで再現可能になります。

また、印刷向けの出力も別途対応できるので、電子版と印刷版の差分も整理しやすくなっています。

## 9. なぜこの設計が執筆者にとって楽なのか

この仕組みが有効なのは、執筆者が扱うべきことが文章だけになるからです。

昔の技術同人誌制作では、文章を書くこと以外にも次のような負担がありました。

- 章の並び順を毎回見直す
- 目次が古いままになる
- 著者紹介が漏れる
- 奥付の項目がズレる
- PDF を見ながらレイアウトの調整をする

こうしたことが、執筆の進捗を阻害します。

対してこのテンプレートでは、

- 記事ファイルを追加するだけで構成に反映される
- タイトルや著者情報が自動で収集される
- 目次や奥付が再生成される
- 最終の PDF もコマンドひとつで作れる

という状態を作っています。これにより、とにかく「本を書き続ける」という体験がしやすくなります。

## 10. 自動化し切れない部分はどこか

自動化の価値が高い一方で、完全に機械がやってくれるわけではありません。

実際には、次のような作業は人手が必要です。

- 表紙のデザインやイラストの調整
- 目次の文章の見直しや、必要な微修正
- 記事間のバランス調整
- 校正と文体の統一
- 印刷会社への入稿用データの最終確認

つまり、ここでの自動化は「執筆者の負担を下げる」ための自動化であって、最終的な品質保証のすべてを置き換えるものではありません。

このプロジェクトの重要な意味は、

- 非執筆作業を減らす
- 誰が何を管理するべきかを明確にする
- 文章の執筆に集中するための土台を作る

という点にあります。

## 11. まとめ

技術同人誌の制作には、本編の執筆以外にも大量の作業が必要です。これは当たり前のことですが、執筆者の視点で見ると、それがかなり不自然で、成果物の完成を遅らせる要因になります。

このプロジェクトは、その問題意識から生まれました。本文を書くことを本来の価値と考え、その他の本の骨格と体裁は自動化して、手作業を減らす設計を採用しています。

具体的には、

- 記事の発見と管理
- title / author / profile の自動収集
- 目次・著者紹介・奥付の自動生成
- 本の構成順の YAML 管理
- Vivliostyle を使った PDF 出力

という流れを、ひとつのテンプレートとしてまとめました。

結果として、執筆者は「本文を書く」ことに集中しやすくなり、編集者は「本全体の整合性を保つ」ことに集中しやすくなります。これは単なる便利さではなく、技術同人誌の制作工程を合理化するための構造です。

技術書は、書くことだけではなく、書籍として成立させることが求められます。だからこそ、執筆の本質に集中できる土台を作ることは、技術同人誌づくりにおいて重要な設計判断だと考えています。

そしてこのテンプレートは、その土台を「コード」で表現したものです。自動化の対象は、文章ではなく、制作の工程そのものです。これが、このプロジェクトの本質です。
