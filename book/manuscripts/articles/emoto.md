# 執筆に専念するための技術同人誌テンプレートの設計

技術同人誌を製作するとき、「本文を書く」以外の作業負担が大きいです。本の製作は執筆だけでなく、組版の調整、目次や奥付の生成など、いくつもの工程があります。本誌のように複数の執筆者がいる場合は、それぞれの記事の調整もあります。これらは本編の執筆と同じくらい大事ですが、どうしても「本文を書く」ことから意識が離れてしまいます。

本誌の製作では、そうした作業をできるだけ自動化しています。執筆者は自身の記事を書くだけです。技術同人誌を作る現場で起きる「非執筆コスト」を削減するように、製作プロジェクトを設計しています。

本誌の製作プロジェクトは執筆テンプレートとして、公開しています。本記事では、そのテンプレートの目的、どのような仕組みで自動化しているのかを、実際のファイル構成と処理の流れにそって説明します。手作業の編集作業が必要になる部分も含めて、どこまで自動化できて、どこからが人手が必要なのかを整理していきます。

## 執筆テンプレートの製作

技術同人誌は、ブログ記事や社内ドキュメントと違い、体裁を整えた書籍として完成させる必要があります。たとえば、次のような作業が発生します。

- 組版（レイアウト）をどうするか
- 記事をどう管理するか
- 奥付に書く項目をどう管理するか
- 表紙画像や PDF の出力設定をどうするか

これらは「本文を書く」とは別の作業ですが、最終的に雑誌自体の品質に直結します。目次や組版などの作業負荷が積み重なると、本来注力すべき執筆が疎かになりえます。そこで、執筆者が本文に集中できるようにと、執筆テンプレートを製作しました。

そのテンプレートは 2023 年ごろに、本の組版や製作を自動でおこなう仕組みとして公開しました。本誌の既刊もこのテンプレートを使って作成してきました。GitHub で管理し、記事の追加や構成の変更は PR ベースで行えるようにしています。

一方で、本誌のような複数人で製作する場合、１つの記事管理ファイルが同時に編集されるという問題ありました。特に締切間近で記事追加の PR が一斉に上がったときは、コンフリクトが毎回発生するため、またか...と頭を悩ませていました。

そこで、今年の夏に、記事管理を含めた自動化を大きく見直しました。執筆者が本文を書くことに集中しやすいように、記事の管理・目次・著者紹介・奥付の生成をより一貫した仕組みに整理し直しています。

## 執筆テンプレートの大まかな流れ

執筆テンプレートの目的は、技術同人誌の制作の「文章を書く」と「本全体の構成や体裁を整える」を分離することです。初回公開時には主に組版や体裁を自動でまかなうテンプレートとしてリリースしましたが、今年の夏に行った大規模な自動化改修では、より広い意味での製作工程の自動化を目指しています。

そのため、テンプレートの流れは次のように整理しています。

1. 執筆者が Markdown で記事を書く
2. Markdown のメタデータ Front Matter にタイトル・著者・プロフィールを記述する
3. 本の構成と目次の順番を YAML で定義する
4. 自動生成スクリプトが目次・著者紹介・奥付を作る
5. 必要に応じて手動で微調整して、PDF を出力する

この流れの重要なポイントは、執筆者が書くべき対象を「本文」だけに絞れることです。目次や著者紹介、奥付は基本的に自動化されるので、書籍の体裁に関する調整が執筆者の思考を妨げることが少なくなります。

最終的には「自動生成したものを人が微調整する」工程は残りますが、それは編集の最後の仕上げであり、執筆の本質ではありません。これはかなり前からやっていた雑務を削減し、執筆者の時間を本文へ向けさせるための設計です。

なお、表示作成はいまだに未対応です。今は生成 AI で自動生成させることもできますが、本誌は社内のデザイナーさんに依頼してます。毎回かっこいい表紙を仕上げてもらっています、改めてありがとうございます！

## テンプレートの全体像

このテンプレートのコアは、執筆者が Markdown で記事を書くと、それを本全体の構成に自動的に反映されることです。

リポジトリの主要なファイル構成は次のとおりです。

```text
book/
└─ manuscripts/
   ├─ articles/
   │  ├─ 執筆者Aの記事.md
   │  :
   │  └─ 執筆者Zの記事.md
   ├─ config/
   │  ├─ articles.yml
   │  ├─ entry.yml
   │  └─ generate.yml
   ├─ generated/
   ├─ edited/
   ├─ pages/
   └─ vivliostyle.config.js
```

それぞれのディレクトリは、次の用途で分かれています。

| ディレクトリ | 役割 |
|:--|:--|
| articles/ | 執筆者が本文を書き込む場所 |
| config/ | 本の構成や見た目のルールを定義する場所 |
| generated/ | 自動生成される目次・著者紹介・奥付の原本 |
| edited/ | 手動で微調整するための編集用コピー |
| pages/ | はじめにやあとがきなどの固定ページ |

執筆者が主に触れるのは articles/ です。ここに Markdown ファイルを置くだけで、テンプレート側が自動で対象として認識し、必要な生成処理に取り込めます。

一方で、config/ は編集者や製作担当が管理する領域で、本の構成順と生成時の見た目を定義します。

| 設定ファイル | 役割 |
|:--|:--|
| <span class="nowrap">articles.yml</span> | 記事の順番を制御する。ファイルがない場合は、articles/ 配下の Markdown ファイルをファイル名順で自動的に扱う。 |
| entry.yml | 本全体の構成順を定義する。目次や固定ページ、記事一覧の配置順などを決める。 |
| <span class="nowrap">generate.yml</span>  | 著者紹介や奥付のテンプレートを定義する。本文の内容ではなく、書籍としての見せ方を決める。 |

また、本のタイトルや著者名などの書籍情報は vivliostyle.config.js で定義します。

このテンプレートでは、執筆者は「どこに何を書けばいいか」を知っていれば十分です。執筆の本質は本文そのものに集中し、構成や体裁、目次や奥付の整合はテンプレート側が担います。編集者が YAML を調整するだけで、製作工程の多くを自動化できる、というのがこのテンプレートの大きな特徴です。

## 文章のメタ情報から本全体を組み立てる

このテンプレートの要は、各記事の Front Matter を読むことです。たとえば各記事は次のような形式で書きます。

```yaml
---
class: content
title: 執筆に専念するための技術同人誌テンプレートの設計
author: 江本光晴
profile: |
  日頃は iOS アプリの開発をやっています。
---
```

ここの title、author そして profile のメタ情報が、後段の自動生成に利用されます。目次では記事タイトルが自動で拾われます。著者紹介ページでは著者ごとのプロフィールがまとめられます。奥付には本のタイトルや版情報が反映されます。

この設計の利点は、本文のときと同じ情報が、別の場所で重複管理されないことです。以前は、目次タイトルや著者紹介文を手作業でまとめていました。見出しや著者情報が変わるたびに、別ファイルを更新しなければならず、編集作業が増えていました。

今回のテンプレートでは、各記事の情報を一か所に書いておくと、その情報が必要な場所に自動で流れます。執筆者がタイトルを変えると目次が変わる。著者名を変えると著者紹介が変わる。プロフィール文を更新すると、著者紹介ページにも反映される。こうして、書籍全体の整合性が自動的に保たれます。

本当に大事なのは、これが「書いたあとに誰かが手作業でまとめ直す」ものではなく、構造的に生成されるという点です。書籍の見た目や情報の整合は、本文とは別のレイヤーで管理されているので、執筆者は本文の内容に集中できます。

## 自動生成されるページ

このテンプレートでは、執筆者が直接編集するのは本文の Markdown に限られます。目次・著者紹介・奥付といったページは、書誌情報と記事のメタ情報から自動生成されます。生成されたファイルは generated/ にそれぞれ配置されます。

### 目次

掲載順とページタイトルから目次を生成します。entry.yml の定義をもとに、固定ページと記事一覧が一本の目次に展開されます。articles エントリがある場合は、その配下の記事タイトルが自動で並びます。

これにより、記事ファイルを追加しただけで、目次が再生成されます。手作業で index.md を更新する必要はありません。

### 著者紹介

各記事の著者名とプロフィールを集約して、著者ごとの紹介ページを作ります。同じ著者が複数の記事を書いていた場合でも、自動的にタイトルを１つにまとめます。

プロフィールの書式も generate.yml で調整できます。profile_template は次のような形式です。

```yaml
profile_template: |
  ### {author}（{title}）

  {profile}
```

ここにある {author} や {title} は、書籍中の各著者プロフィールを整えるためのテンプレート変数です。テンプレートを変えるだけで、著者紹介の見た目を切り替えられます。

### 奥付

書籍のタイトル、発行者、版履歴、連絡先などをまとめて生成します。たとえば generate.yml に次のように定義します。

```yaml
edition_history: 初版

colophon_rows:
  - label: 発行
    value: ゆめみより製作委員会
  - label: 連絡先
    value: https://x.com/yumemiinc
```

奥付の雛形が自動生成されます。ここでの大きな価値は、奥付の項目がデータ化されていることです。手動でメモ帳を開いて調整する必要がなくなり、同じ構成を何度も書き直す心理的な負担が減ります。

## 編集作業を分離する

目次や著者紹介、奥付は自動生成できますが、最終的な本の体裁に合わせて微調整したい場合もあります。そこで、このテンプレートでは、自動生成するファイルと人が編集するファイルを別のディレクトリで管理しています。

自動生成されたファイルは generated ディレクトリに出力されます。生成結果を手動で編集したい場合は、yarn edit を実行して edited ディレクトリにコピーします。編集者は edited ディレクトリにコピーされたファイルを修正します。

なお、この執筆テンプレートのパッケージ管理は、私の好みで yarn v4 を採用しています。Node.js から corepack の同梱が廃止されたので、このまま v6 にするか、別のパッケージマネージャーの移行するか、どうしようかと考えています。

PDF をビルドするときは、edited ディレクトリにファイルがあればそちらを優先し、なければ generated ディレクトリのファイルを使います。このため、次のような運用ができます。

| ディレクトリ | 役割 |
|:--|:--|
| generated | スクリプトが毎回生成するファイルを置く |
| edited | 自動生成されたファイルを手動で調整したものを置く |

この分離によって、記事のタイトルや著者情報を変更したときに自動生成した内容を更新しながら、編集者が加えた最終調整も保護できます。定型的な部分は自動化し、書籍としての仕上げが必要な部分は人が編集できる構造です。

## 本の順番とページ構成も設定ファイルで管理する

本全体の構成は、config ディレクトリにある entry.yml で管理します。ここには、目次や本文、著者紹介、奥付などを、本誌に配置する順番で記述します。

たとえば、次のように定義します。この例では、生成した目次ページの次に「はじめに」の固定ページを置きます。その後に記事一覧を並べ、最後に著者紹介と奥付を配置しています。目次ページ自身、著者紹介や奥付は目次ページに表示しないためので toc: false としています。

```yaml
- type: generated
  id: index
  toc: false

- type: page
  title: はじめに
  file: pages/preface.md
  toc: true

- type: articles
  toc: true

- type: generated
  id: authors
  toc: false

- type: generated
  id: colophon
  toc: false
```

entry.yml の各項目には、配置するページの種類と、目次に表示するかどうかを指定します。

| 項目 | 内容 | 備考 |
|:--|:--|:--|
| <span class="nowrap">type</span> | 配置するページの種類 | generated、page、articles のいずれかを指定する |
| id | 自動生成ページの種類 | generated の場合に index、authors、colophon のいずれかを指定する |
| <span class="nowrap">title</span> | 固定ページや自動生成ページの見出し | page の場合は必須 |
| file | 固定ページの Markdown ファイル | page の場合に指定する |
| toc | そのページを目次に表示するかどうか | true なら表示し、false なら表示しない |

type には、次の３種類があります。

| type | 役割 | 指定する項目 |
|:--|:--|:--|
| <span class="nowrap">generated</span> | スクリプトが生成するページを配置する。 | id で目次、著者紹介、奥付を選ぶ。 |
| <span class="nowrap">page</span> | pages ディレクトリなどに用意した固定ページを配置する。 | title と file を指定する。 |
| <span class="nowrap">articles</span> | articles ディレクトリの記事をまとめて配置する。 | 記事の順番は articles.yml の設定に従い、設定がなければファイル名順になる。 |

こうして本の構造を明示しておくことで、執筆者は「どのファイルをどこに置くか」を意識しなくてよくなります。構成の責務が自動化のレイヤーに移るからです。

## 8. ビルドを簡単にし、出力を再現可能にする

このテンプレートでは、Markdown から PDF を生成するフローを簡潔にしています。

```shell
yarn build
```

これを実行すると、まず自動生成の対象が更新され、その後 Vivliostyle が本を PDF として出力します。つまり、本文の修正や記事の追加をしたあとに、ビルドを実行すればその場で全体の書籍として確認できるのです。

ここで便利なのは、実際の PDF 生成が逐次的な手作業ではなく、一つのコマンドで再現できることです。これにより、同人誌の生成結果が「人に依存する暗黙知」ではなく、コードで再現可能になります。

また、印刷向けの出力も別途対応できるので、電子版と印刷版の差分も整理しやすくなっています。

## 9. なぜこの設計が執筆者にとって楽なのか

この仕組みが有効なのは、執筆者が扱うべきことが文章だけになるからです。

昔の技術同人誌制作では、文章を書くこと以外にも次のような負担がありました。

- 章の並び順を毎回見直す
- 目次が古いままになる
- 著者紹介が漏れる
- 奥付の項目がズレる
- PDF を見ながらレイアウトの調整をする

こうしたことが、執筆の進捗を阻害します。

対してこのテンプレートでは、

- 記事ファイルを追加するだけで構成に反映される
- タイトルや著者情報が自動で収集される
- 目次や奥付が再生成される
- 最終の PDF もコマンドひとつで作れる

という状態を作っています。これにより、とにかく「本を書き続ける」という体験がしやすくなります。

## 10. 自動化し切れない部分はどこか

自動化の価値が高い一方で、完全に機械がやってくれるわけではありません。

実際には、次のような作業は人手が必要です。

- 表紙のデザインやイラストの調整
- 目次の文章の見直しや、必要な微修正
- 記事間のバランス調整
- 校正と文体の統一
- 印刷会社への入稿用データの最終確認

つまり、ここでの自動化は「執筆者の負担を下げる」ための自動化であって、最終的な品質保証のすべてを置き換えるものではありません。

このプロジェクトの重要な意味は、

- 非執筆作業を減らす
- 誰が何を管理するべきかを明確にする
- 文章の執筆に集中するための土台を作る

という点にあります。

## 11. まとめ

技術同人誌の制作には、本編の執筆以外にも大量の作業が必要です。これは当たり前のことですが、執筆者の視点で見ると、それがかなり不自然で、成果物の完成を遅らせる要因になります。

このプロジェクトは、その問題意識から生まれました。本文を書くことを本来の価値と考え、その他の本の骨格と体裁は自動化して、手作業を減らす設計を採用しています。

具体的には、

- 記事の発見と管理
- title / author / profile の自動収集
- 目次・著者紹介・奥付の自動生成
- 本の構成順の YAML 管理
- Vivliostyle を使った PDF 出力

という流れを、ひとつのテンプレートとしてまとめました。

結果として、執筆者は「本文を書く」ことに集中しやすくなり、編集者は「本全体の整合性を保つ」ことに集中しやすくなります。これは単なる便利さではなく、技術同人誌の制作工程を合理化するための構造です。

技術書は、書くことだけではなく、書籍として成立させることが求められます。だからこそ、執筆の本質に集中できる土台を作ることは、技術同人誌づくりにおいて重要な設計判断だと考えています。

そしてこのテンプレートは、その土台を「コード」で表現したものです。自動化の対象は、文章ではなく、制作の工程そのものです。これが、このプロジェクトの本質です。
